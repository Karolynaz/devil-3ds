# Devil-3Ds 3.02 test build

## Crash diagnosis

The 3.01 ARM ELF and 3DSX contain libctru's weak `__stacksize__` default:
**32,768 bytes**. The CIA exheader independently specifies 262,144 bytes.

After hero selection the lobby calls `DvlNet_SendInfoRequest()`, which sends
multicast through lwIP, VirtualTap and ZeroTier. Disassembly of the exact
`d3f2089` debug ELF shows these nested stack frames:

| Function | Local allocation, excluding saved registers |
| --- | ---: |
| `ZeroTier::zts_lwip_eth_tx` | 10,072 bytes |
| `ZeroTier::Switch::onLocalEthernet` | 10,444 bytes |
| `ZeroTier::Multicaster::send` | 82,004 bytes |

The multicast frame alone exceeds the complete 3DSX main stack. Deeper
packet/crypto calls add further usage. This is a concrete overflow path and
is consistent with the reported PC=0 and invalid return addresses. The
screenshot has already reached the lobby, so the hero form is not sufficient
to explain the crash.

The port now uses a strong **1 MiB** main-stack symbol and the same CIA
exheader size, matching the pinned ZeroTier core's `ZT_THREAD_MIN_STACK_SIZE`.
The adapter's default ZeroTier/lwIP thread stacks also use this size; explicitly
sized startup/callback threads retain their existing sizes. These allocations
cost additional memory, not a second render or recurring per-frame work.

The original [DevilutionX protocol implementation](https://github.com/diasurgical/DevilutionX/blob/master/Source/dvlnet/protocol_zt.cpp)
uses the same lwIP virtual socket and multicast discovery path. The network ID
and engine protocol version remain compatible; the port version is separate.
The small-stack problem is specific to how this port launches the library.

## Other changes

- The joining screen heading is translated **Multiplayer**. The status still
  identifies the ZeroTier connection/join operation.
- Main-menu and other list labels tighten spacing before using a smaller
  native bitmap font. Full EN/LT main-menu names fit between the pentagrams;
  text is not rescaled or filtered. Small-font headings are never enlarged.
- Failed virtual socket creation, binding or listening cleans up partial
  sockets and can retry. Discovery reports failed/partial UDP sends as failure
  instead of claiming the request was sent successfully.
- The working update/TLS implementation is unchanged. Update shows **3.02**.

## Verification

- Production menu fitting and line measurement use shipped EN/LT glyph widths.
- Production socket setup/send methods are exercised with failure injection
  under ASan/UBSan, including cleanup and retry.
- Existing heap receive, EOF, settings and multiline alignment checks pass.
- `tools/verify_3ds_stack.py` rejects the old crash build. CI reads the linked
  ARM symbol and the actual 3DSX data and CIA exheader fields, requiring matching
  1 MiB stacks before publishing build artifacts.
- Cross-compilation and bundled asset verification run in the 3DS workflow.

No emulator or console is run by Codex. Public-game discovery and actual
creation/join still require the user's device tests. No GitHub Release is made.

## Device checks

1. Confirm version 3.02 in Update and full title-menu labels in EN and LT.
2. Enter Multiplayer, select an existing hero and leave the lobby open until
   public games load. Repeat with a newly created hero.
3. Create public and password-protected games; join from another compatible
   DevilutionX instance. Desktop game discovery proves neither every session
   nor every game-data combination is compatible, so check the displayed
   engine version and use the same Diablo/Hellfire mode on both ends.
4. If a crash remains, preserve its screenshot and report whether the lobby,
   password form or game itself was visible immediately before the failure.
